# VAL-20261010-030：消息队列插件

日期：2026-10-10。Windows x64 / MSVC v143 / Release。
关联 ADR-015 与消息队列插件实施计划；Production 继续禁用。

## 本批实现

- MQTT 迁至 `plugins/message-queue/mqtt`，保留已有 ID/参数。
- 新增可选 Kafka、RabbitMQ、NATS JetStream ResultOutput。
- 各协议复用异步工具和独立宿主，不把客户端库引入 UI/runtime。
- 消息服务确认与业务确认分别校验；严格关联 event_id/实例/attempt。
- 持久 agent 增加显式非物理幂等准入，复用既有账本与交付状态。
- 固定客户端版本、保留第三方许可正文，记录来源和本地完整性。

## 真实服务与故障对端的区别

Kafka 日常故障测试使用 librdkafka 官方 mock cluster，通过真实 TCP；
不是 Kafka broker。另启动 Apache Kafka 3.9.1 原生 KRaft 单节点、
预建 results/receipts 分区，模拟业务消费者联调 10/10 通过：
durable、success、repeat、broker-only、wrong-id、wrong-attempt、
malformed、oversized、duplicate、process.success。
日志 `out/validation/kafka-native-expanded-20261010.log`。

NATS 测试使用真实 nats-server 2.10.24、JetStream 文件存储、临时端口
及模拟业务消费者；不是手写 NATS 协议对端。

RabbitMQ 日常故障测试使用本仓库有界 AMQP 故障对端。
另以官方 RabbitMQ 3.13.7 Windows ZIP、OTP 26.2.5.15 启动独立本机
broker，10 项正常/故障/宿主/持久测试及 2 项宿主回执故障均通过，共 12 项。
日志：`out/validation/rabbitmq-native-20261010.log`、
`out/validation/rabbitmq-native-process-faults-20261010.log`。
业务消费者为测试程序，测试 results 队列为非持久队列；
这轮联调验证确认语义与互操作，不验证 broker 断电持久性。
服务及消费者均为本机开发测试，不代表真实 MES、集群或现场部署。

真实 Kafka 与 RabbitMQ 联调通过设置 VISION_KAFKA_TEST_ENDPOINT 和
VISION_RABBITMQ_TEST_PORT，复用同一测试可执行文件。默认全量仍使用
受控 Kafka/RabbitMQ 故障对端；NATS 全量自动启动真实 JetStream。
不要将所有故障对端用例强行套到外部服务，它们有不同的故障注入方式。
联调后自建 Kafka、RabbitMQ、临时 NATS 和独立端口的 epmd 均回收。
Erlang 完整 ZIP 哈希与 GitHub 发布 asset digest 一致；
Kafka/RabbitMQ ZIP 的哈希是本地完整性记录，不冒充上游签名校验。

## 失败与修订

1. Windows 初版 Kafka 使用 producev 未在本次客户端构建中得到预期
   投递行为；改用客户端正式 topic/produce API，对端与插件均修订，
   真实服务及 mock 测试通过。不推断所有 Windows producev 都存在问题。
2. Kafka 消费者启动时读取高水位并等待准备完成，避免请求先于测试
   消费者就绪导致假失败；消费者资源用 RAII，启动失败回收 mock。
3. 首次全量 `full-2026-10-10T02-17-26-235Z` 失败：
   GUI 三项持久管线、IPC 六项归档/持久场景出现 TIMEOUT/
   COMMIT_UNCONFIRMED。保留原日志，未删除断言或扩大任务期限。
   此时存在并行下载、编译和原生服务准备，不能据此证明失败原因。
   GUI catch 补 stderr 诊断，随后五项 GUI 持久测试通过。
   最终全量复核见下文，I16 时序观察仍保留。
4. 测试总量增加后，将构建工具对整个 CTest 套件的外层等待上限
   从 180 秒改为 600 秒。单项 CTest 及任务预算保持不变。
5. Docker 后端不可用，WSL 报虚拟化缺失；改用独立原生服务，
   未更改 BIOS、Windows 特性或安装系统服务。
