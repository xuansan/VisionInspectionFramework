# ADR-002：首版模拟场景与设计范围

实施追踪（2026-09-19）：T08两档独立双池传输和故障实验已执行，见[VAL-010](../acceptance/VAL-20260919-010-共享图像与插件宿主验收.md)。采用3秒定速、每帧内容校验，速率接近但略低于目标；不把它当成推理/产线/长稳通过。下文“尚未执行”为当时决策语境。

日期：2026-09-18。状态：采用开发目标；不是实机性能承诺。关联 A02/T01/T04/T08/T30。

## 范围

首条闭环采用两台模拟 2D 面阵相机，每件每相机一帧、两个必需检查项、固定流水线。无真实 PLC 副作用，不包括线扫拼接、3D、跨机器调度或硬实时剔除。

先支持 Mono8 的两档参考配置；未来 RGB/BGR 等格式要独立计算 stride/容量。模拟触发使用明确 trigger_id，不能由随机时间猜工件。

| 参数 | 功能基准 | 图像通路压力基准 |
|---|---:|---:|
| 配置文件 | dual-camera-functional.json | dual-camera-bandwidth.json |
| 相机数/每件每相机帧数 | 2 / 1 | 2 / 1 |
| 单帧尺寸 | 1024×768 Mono8 | 2448×2048 Mono8 |
| 目标工件率 | 10 件/秒 | 20 件/秒 |
| 原始帧吞吐 | 20 帧/秒 | 40 帧/秒 |
| 原始像素流量 | 15,728,640 B/s = 15 MiB/s | 200,540,160 B/s = 191.25 MiB/s |
| 每相机槽位/像素池总量 | 16 / 24 MiB | 16 / 153 MiB |
| 最大在途工件 | 8 | 8 |
| 逻辑检测期限 | 1000 ms | 1000 ms |

队列：控制消息最多 1 MiB，单输出最多 256 事件或 8 MiB，任一达到上限即执行对应过载策略。槽位之外的 SDK 缓冲、预览、掩码、上传和推理内存另行预算。

1000 ms 是失败判定期限，不表示持续负载可排队 1000 ms：在途容量仅 8，平均占用时间过长会提前过载。压力基准要求观测实际容量高水位和延迟，不通过扩大队列掩盖处理不及。

## 实验与实施顺序

当前 JSON 是后续模拟器的目标输入格式，不是完整 RecipeSnapshot，也没有运行器读取它。格式版本 1 保留明确用途。

T04 建立预算验证；T08a 开始时先做简单跨进程图像传递实验，再扩展多消费者：

1. 两档尺寸持续生成固定图样，复制进共享池，消费者校验内容和帧身份。
2. 记录吞吐、端到端分布、CPU、内存、槽位高水位，预览关闭。
3. 注入慢消费者，确认容量拒绝明确、内存受限。
4. 记录 SDK copy/算法/存图加入后的增量开销；不能拿纯图像传递速度冒充推理性能。

没有实测达到目标之前只称“实验目标”。A02 关闭的是提前明确范围；跨进程吞吐实验属于 T08a，当前未执行。

## 未知生产参数与变更

真实相机型号/分辨率、帧数、硬件触发关联、目标节拍/结果截止时间、存图比例、PLC 协议仍需现场确定。确认时间前移至对应设备和数据通路主体设计之前，T30 用于最终验证，不首次决定容量约束。

新增相机路数、线扫、多帧或 GPU 并发需修订本决策和资源预算，不能仅修改 profile 后宣称支持。
