# 工业视觉框架开发

面向框架使用者。先确认项目根目录与用户业务目标，再选用现有模块。
首版可执行模板为Windows模拟上位机和ResultOutput插件；不要把其他接口的存在当成已实现的接入能力。
本Skill与仓库一起分发，脚本只用Python标准库；构建仍使用框架已有工具和依赖。

## 开始

1. 根据用户路径或当前工程定位框架根目录。不能从本Skill的安装位置推断框架路径；允许Skill被单独安装。
2. 执行`python <skill>/scripts/inspect_workspace.py --framework-root <framework>`。
   接口不匹配时先查看差异和当前声明，不改指纹来强行通过。检查通过只代表受支持接口匹配，不代表SDK已安装或生产可用。
3. 阅读框架根目录的`开发进度及计划.md`当前状态及近期队列，再按任务阅读下列资料。
   若存在`.codegraph/`且CodeGraph可用，优先使用它定位代码；没有索引时使用常规搜索，不自动创建索引。

## 按任务读取

- 新建业务应用：先看[应用开发](references/application-development.md)，生成独立业务目录并先跑模拟闭环。
- 新增结果输出：先看[插件开发](references/plugin-development.md)，复用分发及宿主，不把网络/磁盘IO放入主控。
- 判断修改位置、增加其他设备或排错：查[模块地图](references/framework-map.md)和[能力边界](references/capabilities.md)。
- 涉及进程、图像、可靠输出或停止恢复：读[架构规则](references/architecture-rules.md)。
- 任何代码交付：按[测试与交付](references/testing-and-delivery.md)保留真实证据。

## 工作流程

- 从现有信息整理触发来源、相机数量、检测判定、存储、输出、界面和平台。只追问会影响实现的缺项，已有授权不重复询问。
- 说明哪些直接复用、哪些配置、哪些新增，以及验收条件。继承已经批准的方案，不为每个小修改重新组织审批。
- 业务工程放在用户指定的新目录，通过`VISION_EXTENSION_DIR`源码接入。先配置，再应用编排，最后才考虑扩展公共接口。
- 分步实现并验证。正常结果和故障行为一起检查；阶段后执行完整回归。不得只生成占位代码后宣布功能完成。
- 汇报实际改动、构建/测试证据、限制和下一步。未运行的测试写“未运行”，模拟通过不替代实机验收。

## 必须保持的边界

- runtime管运行机制，inspection管检测规则，application管业务编排，插件管具体接入。保持已有依赖限制。
- 插件在独立宿主运行；进程隔离不是恶意代码安全沙箱，也不能保证操作系统/驱动崩溃互不影响。
- 图像通过描述符和租约传递；读进程未退出或未确认停止前不复用槽位。
- 队列、内存、重试和期限有界；不靠删除断言、扩大期限或屏蔽错误让测试通过。
- 检测质量、执行状态、存储状态、输出交付分别报告；不把Pending=0当全部成功，不把HTTP接收当订阅者业务确认。
- 当前Production仍禁用。真实设备、自动图像上传、掩码持久化和完整生产恢复均按最新台账判断，不能由模板默认宣称完成。

## 脚本使用原则

脚本路径相对本Skill，框架/业务路径必须显式传入。脚本拒绝已有目标目录，不修改全局环境、不下载SDK、不上传代码。
生成后的程序和测试在Windows上实际运行；`verify_project.py --scope extension`只做开发定位，正式交付使用默认`--scope all`。
涉及真实PLC动作、覆盖数据、发布或安装依赖，按用户已有授权和环境权限执行；Skill本身不授予额外权限。

本Skill版本与模板受[兼容清单](references/compatibility.json)约束。当前项目许可证未定，模板不替用户选许可证。
